## 1. 前提として確認した事実

### Cloudflareの公式資料で確認したこと

`developers.cloudflare.com` へはこの開発環境から接続できなかったため、同じ内容の公式原稿（GitHubの `cloudflare/cloudflare-docs`、`production` ブランチ）を2026-11-13に読みました。

| 項目 | 公式資料の記載 |
| --- | --- |
| workers.devへのAccess | Worker単位（「Protect this Worker behind Access」）なら、そのWorkerの**ルート、カスタムドメイン、workers.dev、プレビュー**をまとめて保護する。特定のホスト名やパスだけを保護する方法（self-hostedアプリ）もある |
| WorkerでのID確認 | Accessが要求を認証すると、Workerは `ctx.access` で本人情報を読める（JWTの解析不要）。Accessが認証していない要求では `undefined` |
| `ctx.access` の制限 | Accessが**直接**認証した呼び出しだけ。Service Binding・RPCには引き継がれない。Static Assets付きWorkerではユーザーのWorkerに渡らない |
| JWTの検証 | Accessは元のサーバーへの要求に `Cf-Access-Jwt-Assertion` ヘッダーで**アプリケーショントークン**を付ける。公開鍵 `https://<チーム名>.cloudflareaccess.com/cdn-cgi/access/certs` で署名を検証し、発行元（iss）と対象アプリ（aud）を確認する。鍵は6週間ごとに更新、旧鍵は7日間有効 |
| トークンの中身 | `aud`、`email`、`exp`、`iat`、`nbf`、`iss`、`type: "app"`、`sub`（メールごと・アカウントごとに一意な利用者ID）など。サービストークンは `email` ではなく `common_name` を持つ |
| 別オリジンからの通信（CORS） | Accessで保護された先へのCORS要求には `CF_Authorization` Cookieが必要。**第三者Cookieとしてブロックされる場合がある**（シークレットモード、Safari）と注意書きがある。事前確認（OPTIONS）は、Cookieが送られないため403になる。「OPTIONSを元のサーバーへ通す」設定などで対処する |
| Cookie | アプリ用 `CF_Authorization` のSameSite・HttpOnlyは管理者が選べる（既定：SameSite=None、HttpOnly有効）。盗まれたCookieの再利用を防ぐ「Binding cookie」もある |
| セッション | アプリのセッション時間は「すぐ切れる」〜1か月（既定24時間）。全体のセッションは15分〜1か月（既定24時間）。アプリのトークンが切れても、全体のセッションが有効なら自動で再発行される |
| 無効化 | アプリ単位で「既存トークンを取り消す」、利用者単位で「Revoke」ができる。ただし許可ポリシーに残っていれば再ログインできる（**この方式のAPIへの効き方は下の4章の注意を参照**） |

## 2. 採用を推奨する方式

**「ログインだけAccessの画面で行い、Accessが発行・署名したトークンをアプリに渡して、API側のWorkerがそのトークンを毎回検証する」方式**を推奨します。

```text
アプリ（tools.coaching-l.net）              検証用Worker（*.workers.dev）
 ① 「ログイン」をタップ ── 小窓を開く ──▶ /auth/handoff?state=（使い捨ての乱数）
                                          └ Access（パス単位で保護）がメールPINでログイン
                                          └ Accessが署名付きトークンをヘッダーで付ける
                                          └ Workerがトークンを検証（署名・発行元・対象・期限・許可リスト）
 ② アプリの正確なオリジンだけに ◀── postMessage（URLには載せない）── 小窓は自動で閉じる
 ③ API呼び出し ── Authorization: Bearer <Accessのトークン> ──▶ /api/*
                                          └ Workerが毎回すべて検証
                                          └ 通ったときだけ、サーバーのシークレットを付けて上流を呼ぶ
```

### この方式を選ぶ理由

1. **DNSやWordPressを変更せず、Safariの第三者Cookie制限を避けるための有力な候補だから。** アプリとAPIのサイトが違うので、AccessのCookieだけに頼るとSafariでは送られない見込みです（Cloudflareの資料にも注意書きがあります）。Cookieを使わず、ヘッダーでトークンを送れば、第三者Cookieの制限を受けません。実際のAccessログインを経由した動作は、実機で確認します。
2. **独自の認証トークンを作らないから。** 渡すのはAccessが発行・署名したトークンそのものです。署名の鍵はCloudflareが管理し、Worker側に署名用の秘密鍵は不要です。検証方法も公式資料のとおりです。
3. **DNSやWordPressに触れないから。** workers.devのまま使えます。アプリの公開URLも変わりません。
4. **Accessが止まっても開かない作りにできるから。** Workerは、ヘッダーがAccessから来たかどうかに関係なく、毎回署名を検証します。Accessの設定が外れても、偽のトークンでは通りません。

### `ctx.access` を使わない理由

`ctx.access` は、Accessが直接認証した要求でしか使えません。APIの要求（`/api/*`）はCookieが届かないためAccessの保護の外に置く必要があり、`ctx.access` は空になります。そのため、公式資料のもう一つの方法（JWTの検証）を全経路で使います。ログイン小窓（`/auth/handoff`）では `ctx.access` を使える可能性がありますが、経路ごとに確認方法を変えないため、同じ検証にそろえました。

### 独自トークンが必要か

**今回は不要と判断しました。** Accessのトークンをそのまま使えます。ただし次の弱点があります。

- **有効期間がAccessのアプリセッション時間と同じ**です。盗まれると期限まで使われます。そこで、アプリのセッションを短く（例：1時間）、全体のセッションを長め（例：24時間〜7日）にすることを提案します。期限が切れても、全体のセッション中なら小窓が一瞬開くだけで、PINの入力なしに再ログインできます。
- 「この操作だけに使える」ような用途の限定はできません。必要になれば、Workerが数分だけ有効な用途限定トークンを発行する方式を追加できます。その場合は署名用の秘密鍵をWorkerのシークレットに置く必要があります。今回は追加しません。

## 3. 漏れないための設計

| 漏れ先 | 対策 |
| --- | --- |
| URL・ブラウザ履歴・Referer | トークンをURLに載せない。小窓のURLにあるのは使い捨ての `state` だけ（秘密ではない）。応答に `Referrer-Policy: no-referrer` |
| ブラウザの保存領域 | トークンはアプリのメモリだけ。localStorage・sessionStorage・Cookie・Cache Storageに保存しない。再読み込みで消える |
| 別のサイト | 小窓はアプリの**正確なオリジン**にだけ `postMessage` する（`*` を使わない）。アプリ側は、送信元のオリジン・自分が開いた小窓・`state` が一致するメッセージだけ受け取る |
| キャッシュ | 小窓のページとAPIの応答は `Cache-Control: no-store`。Service Workerは別オリジンのPOSTに関与しない |
| ページへの埋め込み | 小窓のページは `frame-ancestors 'none'`・`X-Frame-Options: DENY`、スクリプトはnonce付きのものだけ |
| ログ・エラー | エラー応答は固定の短い文字列だけ。トークン・本人情報・鍵を返さない。Workerはログを出さない（observability無効） |
| 上流のAPIキー | Worker側のシークレット（`UPSTREAM_KEY`）だけが持つ。全部の検証を通った後にだけ付ける |

## 4. API側で毎回確認すること

1. `ENABLED` が `true` で、チームのドメイン（`https://<名前>.cloudflareaccess.com` の形だけ）・対象アプリのAUD（64桁の16進数）・アプリのオリジン・許可メール一覧が正しく設定されている。どれかが欠ければ503（開かない）。
2. 要求元（Origin）がアプリのオリジンと一致する。
3. トークンが `RS256` で、鍵IDがAccessの公開鍵にあり、署名が正しい（`alg: none`・HMAC・偽の鍵は拒否）。
4. 発行元（iss）がチームのドメイン、対象（aud）がこのアプリ、期限内（`exp`・`nbf`・`iat`、ずれは30秒まで）。
5. 利用者のトークン（`type: "app"`、`email` と `sub` あり）。サービストークンは拒否。
6. メールが許可一覧にある。一覧から外せば、まだ期限内のトークンでも**すぐ**拒否。
7. 本文がJSONで4,000バイト以内、入力が条件内。
8. ここまで全部通ったときだけ上流を呼ぶ。公開鍵が取れないときは503で、**上流は呼ばない**。

時刻（`exp`・`nbf`・`iat`）は有限の数値に限ります（`exp` は必須、`nbf`・`iat` はあれば検査）。文字列や、JSONの解析で無限大になる値は、正しい署名があっても拒否します。

公開鍵の取得は、未認証の要求でWorkerの処理や外への通信が増えないようにしています。同時に来た要求は1回の取得を待ち合わせ、取得は5秒で打ち切ります。取得に失敗したときや、知らない鍵IDのトークンが来たときも、次の取得までは60秒空けます（その間は503または401）。ただし、これは1つのWorkerの実行単位（isolate）の中での制限で、Cloudflareの拠点をまたいだ全体の制限ではありません。公開鍵は取得先（チーム）ごとに別々に保管し、取得の結果は、その取得を始めたチームの保管場所にだけ書き込みます。設定だけを変えたとき、Cloudflareは同じ実行単位を使い続けることがあるため、チームの設定を切り替えた最中に古いチームの取得が遅れて終わっても、新しいチームの鍵が上書きされないようにしています。

**取り消し（Revoke）について：** WorkerはAccessの取り消し状態を問い合わせません。そのため、**Accessの管理画面で「Revoke」しても、すでに渡したトークンはその期限（と30秒の許容時間）まで、このAPIで使えます**。止めたいときは、(1) Workerの許可メール一覧から外す、(2) `ENABLED` を `false` にする（全員を止める）、のどちらかを使います。どちらも**設定の変更がWorkerに反映された後の、新しい要求**に効きます。反映にかかる時間や、すでに上流へ送った処理を止めることまでは保証しません。将来は、サーバー側の失効管理（利用量台帳と同じ場所）を検討します。

将来の利用量台帳（Durable Objects）では、利用者の識別に**発行元（`iss`）と `sub` の組**を使い、メールは許可の確認と表示用に分けます。`sub` は、利用者を削除して再追加すると変わります。台帳は、認証の後・上流を呼ぶ前に利用枠を予約し、台帳が使えないときは止める設計にします（今回のPoCには予算の保護はまだありません）。

## 5. 迂回経路への対策

- `/api/*` はAccessの保護の外に置きますが、**Worker自身がすべての要求を検証**します。workers.devでも、プレビューURLでも、どのURLから来ても同じ検証を通ります。
- それでも、プレビュー（バージョン）URLは管理画面で無効にするか、Accessで保護してください。先行調査では、翻訳Workerのプレビューは無効でした。
- 本番の翻訳Worker（`coaching-l-translation`）には手を入れていません。そちらは今も未認証で使えます（REVIEWのSEC-001）。認証を本番に入れるときは、翻訳Workerへの未認証の入口を残さないように切り替えます。

## 6. 自動テストで確認したこと（ローカル・モック）

`npx playwright test tests/auth-poc.spec.js` で確認します。Accessの公開鍵はテストの中で作った鍵、上流は呼び出し回数を数えるだけのモックです。

- 許可された人：上流を**1回だけ**呼び、上流へのキーはWorkerだけが付ける。
- 未ログイン、JWTでない、偽の署名（同じ鍵IDの別の鍵）、期限切れ、有効期間前、発行時刻が未来、別のアプリ（aud）、別のチーム（iss）、サービストークン、`alg: none`、HMAC、未知の鍵ID、許可一覧にない人：すべて拒否し、**上流は0回**。応答にトークンを含まない。
- 許可一覧から外すと、期限内のトークンでもすぐ拒否（テストでは設定を変えた次の要求から）。
- 公開鍵が取れないとき、設定が欠けている・不正なとき：拒否し、上流は0回。
- 時刻が文字列・オブジェクト・無いもの・無限大になるもの：正しい署名でも拒否、上流は0回。
- チームの設定を切り替えた最中に、古いチームの鍵の取得が遅れて終わっても、新しいチームの正しいトークンは通り、古いチームの鍵で署名して新しいチームを名乗るトークンは拒否される。
- 公開鍵の取得：同時に20件来ても取得は1回。取得に失敗した状態で10件来ても取得は1回（すべて503）。60秒後に1回だけ取り直し、成功すれば通る。鍵が新しいものに替わったとき、60秒の間は新しい鍵のトークンを拒否して取り直さず、その後1回取り直して通る。
- 別のサイトから、Originなし、GET、大きすぎる本文、空の本文：上流は0回。事前確認（OPTIONS）は正しいヘッダーで204、Cookieを許可しない。
- ログイン小窓：検証済みの人にだけトークンを渡す。偽のヘッダー（Accessが外れた状況）、未ログイン、許可外、不正な `state` では渡さない。URLの転送なし、`no-store`、CSPあり、送り先はアプリの正確なオリジン。
- ブラウザ（Chromium、AndroidとWebKitの設定はCI）：アプリと API を別オリジンに置き、Accessの役をテスト用サーバーが代わりに務めて、小窓→トークン受け取り→API呼び出しまで通る。トークンはlocalStorage・sessionStorage・Cookie・URLに残らない。ログアウト後は呼べない。許可外の人と、小窓以外からの偽メッセージでは、ログインもAPI呼び出しも起きない。

- ログイン待ちの間にログアウトすると、遅れて届いた正しい通知は無視され、ログイン状態に戻らない。
- 小窓からの通知は「送信元のオリジン」「自分が開いた小窓」「この試行の `state`」の3つがすべて合うときだけ受け取る。正しい通知が受け取られること（対照）と、1つだけ違う通知（オリジンだけ違う・窓だけ違う・`state` だけ違う）がそれぞれ無視されることを確かめた。
- テストは外に出ない：Node側では想定外のURLへの通信を失敗させ、ブラウザ側ではテスト用の2つのサーバー以外への通信を遮断し、どちらも0件であることを毎回確かめる。ブラウザの遮断は転送（リダイレクト）も通さない：許可したサーバーからの転送はブラウザに返し、次の要求をもう一度確かめる。許可したサーバーから別のローカルサーバーへの転送が止まることを、対照のテストで確かめた。Accessのログイン画面もローカルの代役。

テストが本当に失敗を見つけるかも確かめました。対象アプリの確認・署名の確認・許可一覧・小窓の確認、公開鍵の取得の待ち合わせと再取得の間隔、時刻の型の確認、ログアウト時の取り消し、小窓からの通知の3つの確認をそれぞれわざと外すと、対応するテストが失敗しました（コミットには含めていません）。

## 9. 管理画面で必要になる操作（今回は実施しない・承認待ち）

3. 検証用Worker `coaching-l-auth-poc` を新しく作成（本番の翻訳Workerとは別）。プレビューURLを無効化。
4. Accessで、self-hostedアプリを作成：対象は `coaching-l-auth-poc.<アカウント>.workers.dev/auth/*` だけ。ポリシーは「管理者のメール1件だけを許可」。アプリのセッション時間を短めに設定。
5. 作成したアプリのAUDタグと、チームのドメインを、Workerの変数に設定。許可メール一覧に管理者のメールを設定。上流は、本物のAPIではなくモック（またはなし）のまま。

## 10. 費用

- 検証用Workerを試す場合：Workers Freeの範囲で収まる見込みです。AccessはZero Trustの無料プランで少人数なら無料で使える見込みですが、**利用可能人数と現在の契約は、実アカウントで未確認**です。有料プランへの変更は行いません。
